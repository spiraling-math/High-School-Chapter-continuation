# SPI-Math Question Bank Platform — Export Standard

**Status:** Active
**Scope:** Defines every supported export target, the rules each must obey, and the contract that guarantees exports remain reproducible, offline-capable, and round-trippable back into the canonical bank.
**Audience:** Engineers implementing exporters, reviewers approving new export formats, integrators consuming exports.

---

## 1. Purpose and Principles

The platform generates, stores, and exports **original mathematics questions**. An export is never just a rendered artifact — it is a transport of structured mathematical data plus (optionally) a presentation layer. Every export MUST honor the following principles.

| Principle | Requirement |
|-----------|-------------|
| **Reproducible** | The triple `{generatorId, generatorVersion, seed}` plus `config` travels with every exported item. Any item can be regenerated byte-for-byte from these. |
| **Offline-first** | Interactive HTML exports work by double-clicking a local file. No CDN, no live server, no network call is permitted at runtime. |
| **No secrets** | No API key, database credential, access token, signed URL, internal hostname, or environment value may appear in any exported file. Exports are treated as publicly distributable. |
| **Data ≠ presentation** | Exports MUST include the structured mathematical data, never only pre-rendered text. Rendered output (KaTeX HTML, SVG) is a derived convenience layer, always accompanied by its source data. |
| **Self-describing** | Every structured export carries a `schemaVersion` and an `exporterVersion` so a consumer can interpret it without out-of-band knowledge. |

**KaTeX** renders math; **SVG** renders diagrams. Both are derived from canonical source fields (`latex`, `diagramSpec`). The canonical bank format is structured JSON.

## 2. Export Target Catalog

For each target: **purpose**, **contents**, **file structure**, **round-trippable** (can it be re-imported losslessly into the bank?), and **offline behavior**.

### 2.1 Self-contained Interactive HTML

| Field | Value |
|-------|-------|
| **Purpose** | A portable, single-file interactive assessment that runs by double-clicking locally. |
| **Contents** | Structured item data (embedded JSON island), KaTeX CSS+JS inlined, fonts inlined as base64, SVG diagrams inline, app JS for navigation/answer-entry, local save/load logic. |
| **File structure** | One `.html` file. A `<script type="application/json" id="bank-data">` block holds the canonical item array; all assets inlined in `<style>`/`<script>`. No sidecar files. |
| **Round-trippable** | **Yes.** The embedded JSON island is canonical and can be extracted and re-imported. The rendered layer is ignored on import. |
| **Offline behavior** | Fully offline. Zero network requests. Persists user state via IndexedDB and can import/export `.json` data files via the File System Access API or a download/upload fallback. |

### 2.2 Printable HTML

| Field | Value |
|-------|-------|
| **Purpose** | Browser-printable assessment with controlled pagination. |
| **Contents** | Rendered questions + a print stylesheet; embedded JSON island for data fidelity. |
| **File structure** | One `.html` file with `@media print` rules, page-break controls, and inlined assets. |
| **Round-trippable** | **Yes** (via embedded JSON island). |
| **Offline behavior** | Fully offline. Designed to be legible in grayscale; never relies on color alone. |

### 2.3 Student Worksheet

| Field | Value |
|-------|-------|
| **Purpose** | Hand-out for students: questions and answer spaces only. |
| **Contents** | Question stems, figures, blank answer regions/working space. **No solutions, no answer key, no hidden answer fields.** |
| **File structure** | Printable HTML (see 2.2) filtered to the student view; embedded JSON island excludes solution/answer fields. |
| **Round-trippable** | **Partial.** Re-importable as items, but solutions are intentionally absent — not a source of truth for solutions. |
| **Offline behavior** | Fully offline. Print-optimized. |

### 2.4 Answer Key

| Field | Value |
|-------|-------|
| **Purpose** | Compact list of correct answers for fast marking. |
| **Contents** | Item id + final answer (and mark value). No working shown. |
| **File structure** | Compact printable HTML table, one row per item; optional embedded JSON island. |
| **Round-trippable** | **Partial.** Answers re-importable; full item bodies not present. |
| **Offline behavior** | Fully offline. |

### 2.5 Worked-Solution Document

| Field | Value |
|-------|-------|
| **Purpose** | Teacher/marker reference with full structured solutions. |
| **Contents** | Question, step-by-step structured solution, mark scheme (marks per step, acceptable alternatives, common errors). |
| **File structure** | Printable HTML; solution steps are structured data, each rendered via KaTeX. Embedded JSON island includes the full solution objects. |
| **Round-trippable** | **Yes.** |
| **Offline behavior** | Fully offline. |

### 2.6 Question-Bank JSON (Canonical)

| Field | Value |
|-------|-------|
| **Purpose** | The source of truth. Full, lossless representation for storage and re-import. |
| **Contents** | Complete item objects: stem, choices/answer, structured solution, `latex`, `diagramSpec`, objective ids, `{generatorId, generatorVersion, seed, config}`, review state, dates, tags, content hash. |
| **File structure** | A `.json` document validating against `question-item.schema.json` (and `assessment-blueprint.schema.json` for assessment containers). UTF-8, stable key ordering. |
| **Round-trippable** | **Yes — canonical.** This is the definitive re-import format. |
| **Offline behavior** | N/A (pure data); consumed by the app, no network. |

### 2.7 Metadata CSV

| Field | Value |
|-------|-------|
| **Purpose** | Spreadsheet-friendly catalog / reporting. |
| **Contents** | One row per item. Columns: `id, objectiveIds, generatorId, generatorVersion, seed, difficulty, reviewState, createdDate, modifiedDate, tags, contentHash`. |
| **File structure** | UTF-8 CSV with header row; multi-valued cells (objectiveIds, tags) use a documented delimiter (`;`) inside the field. |
| **Round-trippable** | **No (lossy).** Metadata only — does not contain question bodies. Use for indexing/audit, not reconstruction. |
| **Offline behavior** | N/A. |

### 2.8 Assessment Blueprint JSON

| Field | Value |
|-------|-------|
| **Purpose** | Defines the structure of an assessment: sections, item selection rules, mark totals, ordering. |
| **Contents** | Section definitions, objective coverage targets, difficulty distribution, per-section mark totals, item references or selection constraints. |
| **File structure** | `.json` validating against `assessment-blueprint.schema.json`. UTF-8, stable key ordering, `schemaVersion`. |
| **Round-trippable** | **Yes.** Re-importable to reconstruct or regenerate an assessment. |
| **Offline behavior** | N/A. |

### 2.9 QTI-Compatible Format (Reserved)

| Field | Value |
|-------|-------|
| **Purpose** | Interoperability with external LMS/assessment systems. |
| **Contents** | Unknown / to be decided. |
| **File structure** | Likely **QTI 3.0** package (IMS Question & Test Interoperability). |
| **Round-trippable** | To be decided — QTI is lossy relative to our generator metadata; round-trip likely requires preserving our `{generatorId, version, seed}` in QTI extension/metadata fields. |
| **Offline behavior** | To be decided. |
| **Status** | **Reserved. Not in first release.** Architecture must not preclude it. |

## 3. Canonical JSON Export Rules

All structured JSON exports (2.6, 2.8, and the embedded islands of 2.1/2.2/2.5) MUST:

1. **Validate** against the relevant schema: `question-item.schema.json` for items, `assessment-blueprint.schema.json` for blueprints. Export fails (hard error) if validation fails.
2. **Carry a `schemaVersion`** field at the document root (semantic version string, e.g. `"1.0.0"`).
3. **Use stable key ordering** — keys serialized in a fixed, documented order (recommended: lexicographic) so that diffs are meaningful and byte-stable across runs.
4. **Be UTF-8 encoded**, no BOM, LF line endings.
5. **Use canonical number/string formatting** — no insignificant whitespace differences, consistent escaping — so re-export of unchanged data is byte-identical.

---

## 4. Reproducibility Contract

Every exported item MUST be regenerable from:

```
{ generatorId, generatorVersion, seed, config }
```

Rules:

- **Exporters MUST include** all four fields for every item. An item missing any of them fails export validation.
- **Determinism guarantee:** running `generatorId@generatorVersion` with the same `seed` and `config` reproduces the item exactly (same stem, same answer, same diagram).
- **Generator no longer exists / version unavailable (graceful degradation):**
  - The export MUST still include the **last rendered fallback**: the structured fields plus the previously rendered KaTeX/SVG output captured at generation time.
  - The item MUST be flagged: `reproducible: false` with `reproducibilityNote` explaining the missing generator version.
  - Consumers display the stored rendered fallback and surface the flag; they MUST NOT silently attempt regeneration with a different version.
- **Config completeness:** `config` must capture every input that affects output (locale is fixed to English; no localization variance). Any non-deterministic source (clock, RNG outside the seed) is prohibited inside generators.

---

## 5. Standalone HTML Bundling Requirements

For the self-contained interactive and printable HTML targets:

- **Asset inlining:** KaTeX CSS and JS, all fonts (base64 data URIs), CSS, app JS, and SVG diagrams are inlined into the single `.html`. No relative or absolute external references.
- **No network calls:** No `<script src=...>`, `<link href=...>`, `@import url(...)`, `fetch`, `XMLHttpRequest`, `WebSocket`, or `Image()` pointing off-document. Build step MUST scan output and fail if any external URL (http/https/protocol-relative) is present, except documented inert namespace URIs (e.g. `http://www.w3.org/2000/svg`).
- **Content Security Policy:** ship a restrictive meta CSP, e.g.:
  ```
  default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline';
  img-src data:; font-src data:; connect-src 'none'
  ```
  `connect-src 'none'` enforces the no-network rule at runtime. (`'unsafe-inline'` is required because assets are inlined; this is acceptable for a local, no-network artifact.)
- **Local persistence:** user/session state stored in **IndexedDB** keyed per assessment. No server, no cookies for data.
- **Import/export of `.json` data files from within the app:**
  - Export: serialize current state to a canonical JSON file and trigger a download (or File System Access `showSaveFilePicker`).
  - Import: load a user-selected `.json`, validate against the schema, and rehydrate. Reject files that fail validation with a clear message.
- **No secrets:** the embedded data island and app JS are inspectable by anyone; they must contain only question/assessment data — never credentials, keys, or internal endpoints.

## 6. Print and Pagination

- **Page-break control:** use `break-before`/`break-after`/`break-inside: avoid` so a question and its answer space are never split across pages.
- **Section/question grouping:** sections start on a controlled boundary; each question is an atomic, non-breaking block where size permits.
- **Headers/footers:** running header (assessment title, version) and footer (page X of Y, item count) via print margins.
- **Mark totals:** per-section and grand-total marks printed; teacher version shows per-question marks.
- **Two-version output:**
  - **Student version:** questions + answer spaces, no solutions/marks-per-step.
  - **Teacher version:** questions + worked solutions + mark scheme + answer key.
  - Both derive from the same canonical data; they differ only in which fields render.
- **Diagrams:** SVG remains vector and high-resolution in print — must stay crisp and legible at print DPI. No rasterization that degrades clarity. Legible without color (use line style/labels, not color alone, to convey meaning).

---

## 7. Determinism and Integrity

- **Content hash (optional per item and per assessment):** a hash (e.g. SHA-256) computed over the **canonicalized** structured data (stable key order, normalized formatting), excluding volatile fields (timestamps, the hash field itself).
- **Uses:**
  - **Tamper-evidence:** consumers recompute the hash to detect modification of an exported item/assessment.
  - **Duplicate detection:** identical mathematical content yields identical hashes, enabling dedupe across banks and exports.
- The hash is stored as `contentHash` in canonical JSON and the metadata CSV. Because canonical JSON is byte-stable (§3), hashes are stable and comparable.

---

## 8. PDF

- **PDF is deferred. Not in first release.**
- The architecture MUST keep PDF feasible later **via the print pipeline** — i.e. the Printable HTML target (§2.2, §6) is the intended PDF source. A future PDF exporter renders the print HTML through a headless engine; no separate layout system.
- Do not introduce a parallel PDF layout path now. If a source document later mandates PDF earlier, it is added as a new versioned exporter consuming the existing print HTML.

---

## 9. Versioning of Export Formats

- **Each exporter carries its own `exporterVersion`** (semantic version), recorded in every artifact it produces (in the JSON root, an HTML `<meta>` tag, or a CSV provenance comment/column).
- **Never silently change the meaning of an export format.** Any change to field semantics, layout contract, or structure is a version bump:
  - **Patch:** bug fix, no semantic/structural change.
  - **Minor:** additive, backward-compatible fields.
  - **Major:** breaking change to structure or meaning; consumers must be notified and migration documented.
- `schemaVersion` (data shape) and `exporterVersion` (the producing tool) are tracked independently. A changelog entry is required for every minor/major bump.

---

## 10. Acceptance Checklist for Any New Exporter

A new exporter is accepted only when ALL of the following hold:

- [ ] **Reproducibility:** every item carries `{generatorId, generatorVersion, seed, config}`; missing-generator path produces rendered fallback + `reproducible:false` flag.
- [ ] **Data over presentation:** output includes structured data, never only pre-rendered text (or is explicitly documented as a lossy/partial target, e.g. CSV/answer key).
- [ ] **Schema validation:** any JSON validates against `question-item.schema.json` / `assessment-blueprint.schema.json`; carries `schemaVersion`.
- [ ] **Canonical serialization:** UTF-8, stable key ordering, byte-stable re-export.
- [ ] **Round-trip declared:** the export documents whether it is fully, partially, or not round-trippable.
- [ ] **Offline (if HTML):** no external URLs; passes the no-network build scan; restrictive CSP with `connect-src 'none'`; works by double-clicking.
- [ ] **No secrets:** automated scan confirms no API keys, credentials, tokens, signed URLs, or internal hostnames in output.
- [ ] **Print (if printable):** page-break control, two-version (student/teacher) support, high-resolution legible diagrams, legible in grayscale.
- [ ] **Integrity:** `contentHash` computed over canonicalized data where applicable.
- [ ] **Versioning:** exporter sets `exporterVersion`; changelog entry added; no silent meaning change.
- [ ] **English only:** no Arabic/RTL/localization in output or tooling.
- [ ] **Tests:** golden-file test proving byte-stable output and a re-import test for round-trippable targets.
